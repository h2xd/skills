# Triage

Issue #212 says "export is broken". Nobody knows if it is a bug, if it is
already fixed, or who picks it up. Triage gives it one category, one state,
and, when it is ready, a brief an agent can work from weeks later without
asking anyone. A PR is an issue with attached code, with the same roles and states.

## Roles

| Role | Kind | Meaning |
|---|---|---|
| `bug` | category | Something is broken |
| `enhancement` | category | A new feature or an improvement |
| `needs-triage` | state | The maintainer has to evaluate it |
| `needs-info` | state | Waiting on the reporter |
| `ready-for-agent` | state | Fully specified. An agent can do it without a person |
| `ready-for-human` | state | Specified, but a person has to do it |
| `wontfix` | state | Will not be done. Closed |

These are role names. The label string for each role is in the `## Triage`
section of `docs/agents/issue-tracker.md`. For a PR, `ready-for-agent` means an
agent takes the next step on the diff, and `ready-for-human` means a person merges.

- A triaged issue carries exactly one category and one state.
- An unlabeled issue goes to `needs-triage`, and from there to any state.
- `needs-info` goes back to `needs-triage` when the reporter answers.
- An `idea` issue stays out of triage, per `../plan-grill/idea-issue.md`.
- Every comment you post starts with `> *This was generated by AI during triage.*`

## Steps

### 1. Load the setup

Read `docs/agents/issue-tracker.md`. Find the operations, the label per role,
the PR flag, and who counts as external. When the `## Triage` section is
missing, stop. Tell the user to re-run setup, per `../setup/SKILL.md`.
Done when you can name all seven label strings and whether PRs are in scope.

### 2. Show what needs attention

When the user asks what needs attention, or names nothing, use **List by
label** and **Search**. Show three buckets, oldest first, one line per item:

1. **Unlabeled.** Never triaged.
2. **`needs-triage`.** Evaluation started.
3. **`needs-info` with a reporter reply** after the last triage notes.

Leave out every issue with the `idea` label. When PRs are in scope, add
external PRs, and tag each line `[PR]` or `[issue]`. For "what is ready for an
agent", list `ready-for-agent` instead.
Done when the user picked an item, or has the list they asked for.

### 3. Gather context

1. Read the issue in full with **View**: body, comments, labels, author,
   dates. For a PR, read the diff too.
2. Read earlier triage notes, per Resuming in [`comments.md`](comments.md).
3. Read the code the request touches. Name things by their glossary headings,
   per `h2xd:docs-glossary`. Find decision records on that code with
   `node scripts/find-docs.ts --type Decision --links-to <path>`.
4. **Already built?** Search the code by the domain concept, not only the
   reporter's words. Note where you looked.
5. **Rejected before?** Run `node scripts/find-docs.ts --type Decision --search "<words>"`.
   Run **Search** on closed issues with the `wontfix` label string. Read
   their closing comments. Handle a match as [`comments.md`](comments.md) says.

Done when you can say what the code does today, whether it already does what
is asked, and which records or closed issues match.

### 4. Recommend

Give the category, the state, the reason, and what step 3 found: code paths,
matching records, prior rejections. Ask the user to confirm or redirect.
Done when the user named a direction.

### 5. Verify the claim

- **Bug.** Reproduce it from the reporter's steps.
- **PR.** Check out its head in a separate git worktree. Run the tests or the
  commands that show the diff does what it claims.
- **Enhancement.** Confirm the current behavior the request describes.

Report one result: confirmed with the code path, not reproduced, or not
enough detail. Not enough detail points to `needs-info`.
Done when the result is stated with the commands you ran.

### 6. Grill when needed

When the request is still open in shape, grill it with `h2xd:plan-grill`.
Record terms with `h2xd:docs-glossary` and decisions with `h2xd:docs-adr`
as they settle. Skip this step for `needs-info` or a complete request.
Done when the grill's decision table is confirmed, or you said why you skipped.

### 7. Apply the outcome

Draft the comment in a scratchpad file. Show it with the label changes.

| State | Comment, from | Then |
|---|---|---|
| `ready-for-agent` | Agent brief, [`brief.md`](brief.md) | Set the labels |
| `ready-for-human` | Human brief, [`brief.md`](brief.md) | Set the labels |
| `needs-info` | Triage notes, [`comments.md`](comments.md) | Set the labels |
| `wontfix` | Closing comment by reason, [`comments.md`](comments.md) | Set the labels, then **Close** |
| `needs-triage` | Only when there is partial progress | Set the labels |

On a yes, use **Comment**, then **Label**. Add the new labels and remove the old state.
Done when **View** shows the comment and exactly one category and one state.

## Moving an issue directly

When the user says "move #42 to `<state>`", skip steps 3 to 6. Show the label
change and any comment, then apply them on a yes.

- When the issue has the `idea` label, say so and stop.
- When the move is to `ready-for-agent` and no brief exists, ask whether to write one.
- When an issue carries two states, or a move skips the usual path, say so and ask.

## Report

After a session, one line per issue, worst first:

```
🔴 #<n>: <blocked: conflicting states, a failed post, a claim that did not reproduce>
🟡 #<n>: <needs-info or needs-triage, and what is missing>
🟢 #<n>: <the new state, and the comment posted>
```

## Do

- Read earlier triage notes before you ask anything.
- Search the code by concept before you call a request new.
- Verify the claim before you grill or write a brief.
- Show every comment and label change before you post it.

## Don't

- Don't use the role names as labels. Use the strings from `docs/agents/issue-tracker.md`.
- Don't post without the AI disclaimer line. Start every comment with it.
- Don't leave an issue with two states. Remove the old one in the same step.
- Don't triage an `idea` issue. Leave it until someone removes the label.
- Don't list a collaborator's PR in step 2. Show external PRs only, unless the user names one.
- Don't record an already-built request as a rejection. Close it with a pointer to the code.
- Don't ask the reporter for "more info". Ask specific questions.
