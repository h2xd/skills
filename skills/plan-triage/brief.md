# Briefs

A brief is the comment posted when an issue moves to `ready-for-agent` or
`ready-for-human`. It is the contract, and the issue body and discussion are
context. An agent may pick the issue up weeks later, in a codebase that has
changed since.

For an issue, the brief says what to build. For a PR, it says what is left to
do on the existing diff: finish it, close gaps, address review points.

## Rules

- **Behavior, not procedure.** Say what the system does when the work is
  done. The agent reads the code itself and picks the implementation.
- **Names that last.** Name types, function signatures, commands, config keys
  and glossary terms by their glossary heading. Name decision records by
  number, such as `ADR-0007`.
- **No file paths, no line numbers.** They go stale while the issue waits.
- **Testable acceptance criteria.** Each one can be checked on its own: a
  command and its output, an input and its result.
- **Out of scope, stated.** List the neighboring changes the agent leaves
  alone.
- **Verification result.** Say what step 5 confirmed, so the agent does not
  repeat it.
- **Short.** Follow [`../setup-tone/github-text.md`](../setup-tone/github-text.md).
  Open with `## Summary`. Use bullets, not paragraphs. The whole brief fits on
  one screen.

## Agent brief

The first summary bullet names the brief, so a later session can find it.

```markdown
> *This was generated by AI during triage.*

## Summary

- Agent brief for a <bug | enhancement>.
- <What has to happen, in one line.>

🔴 <what is broken now>
🟡 <what is partial>
🟢 <what triage verified>

## Current behavior

- <What happens now. For a bug, the broken behavior and how it was reproduced.>
- <For a PR, what the diff already does and the gaps it leaves.>

## Desired behavior

- <What happens after the work, one bullet per behavior.>
- <Edge cases and error conditions, one bullet each.>

## Key interfaces

- `<TypeName>`: <what changes and why>
- `<functionName()>`: <what it returns now, and what it returns after>

## Acceptance criteria

- [ ] <one checkable criterion>
- [ ] <one checkable criterion>

## Out of scope

- <a change the agent leaves alone>

## Constraints

- <a decision record that applies, by number. Leave the section out when none apply.>
```

Give only the status lines that apply.

## Human brief

Use the same template. The first summary bullet reads
`Human brief for a <bug | enhancement>.` Add one section after the status
lines:

```markdown
## Why a person

- <the judgment call, outside access, design decision or manual test an agent cannot do>
```

## Example: a PR

```markdown
> *This was generated by AI during triage.*

## Summary

- Agent brief for an enhancement.
- Finish the contributor's `--json` flag for `report list`.

🟡 Errors still print as plain text, and the flag has no test.
🟢 The success path prints valid JSON. Triage ran it on the PR head.

## Current behavior

- The PR adds `--json`, which prints the report list as JSON.
- Errors print as plain text, even with `--json`.

## Desired behavior

- With `--json`, all output, errors included, is valid JSON on stdout.
- Exit codes are the same as without the flag.
- Output without the flag is unchanged.

## Key interfaces

- The command's error path prints `{ "error": string }` under `--json`.
- Reuse the serializer the PR adds. Do not add a second one.

## Acceptance criteria

- [ ] `report list --json` prints valid JSON on success and on error
- [ ] Exit codes match the command without `--json`
- [ ] A test covers the JSON success output and one error
- [ ] Output without `--json` is byte-for-byte unchanged

## Out of scope

- `--json` on other commands
- The shape of the success payload the PR defines
```

## A brief that fails

```markdown
## Agent brief

**Summary:** Fix the report bug

The report thing is broken. Look at src/report/handler.ts around line 150.
```

This brief has no disclaimer, no category, and no current or desired
behavior. Its file path and line number will go stale. It has no acceptance
criteria and no scope.
